# 実装の前に、計画を Codex と詰める

## Triggers

- 新しい機能、挙動を変える修正、schema・CI・release・依存の変更に入る前
- 持ち主が「Codex と詰めて」「計画を作って」と言ったとき

## Does not trigger

- 実装の後の差分レビュー（`codex-review`）
- 文書・設定の整理、リネームなど、挙動を変えない可逆な作業

## 1. 対象を確かめる

- 何を作る・直すかと、持ち主の決定事項（議論の対象にしない）を書き出す
- コードと一次情報を先に読み、参照したファイルと URL を控える

## 2. 叩き台を書く

scratchpad に計画を書く。Codex への依頼文と出力も scratchpad に置く。節は「目的 / 対象外 / 方針 / 手順 / 検証（何で確かめるか）/ リスク / 未解決の問い」。

## 3. 1 往復目（独立の評価）

```bash
codex exec -s read-only - < <依頼文> > <出力> 2>&1
```

- `--ephemeral` を付けない（付けると続きを話せない）。出力の先頭の `session id:` を控える
- 依頼文に入れるのは、持ち主の要求・決定事項・叩き台・参照先だけ。Claude の予想反論や結論は入れない
- 返す形を頼む: 項目ごとの「賛成 / 反対（理由と代案）/ 抜け」、確かさ（一次情報で確認 / 推測）、合意できる点と割れる点
- Bash の `run_in_background` で投げ、完了の通知を待つ。1 往復 10〜15 分。途中で止めない
- 終了コードが 0 でない、`tokens used` の後の答えが無い、`session id` が無い、のどれかなら失敗とみなす。同じ依頼文で 1 度だけ
  やり直し（2 往復目以降は同じ id で再開）、それでも失敗したら議論を止めて持ち主へ報告する。合意していない計画を 6 で共有しない

## 4. 2 往復目以降（議論）

```bash
codex exec resume <session id> -c 'sandbox_mode="read-only"' - < <依頼文> > <出力> 2>&1
```

- **`-c 'sandbox_mode="read-only"'` を毎回付ける。**付けずに再開すると `workspace-write` になり、Codex が書き込める（実測）
- `--last` ではなく控えた id で再開する
- 指摘に ID を付け、ID ごとに「受理 / 根拠付き反論 / 保留」と、計画の変更箇所を渡す
- 事実で決められる点は、Claude か Codex が実測して決める
- 終わる条件: 直した計画について、重大な未解決点が無いことを Codex が確かめた。争点が無ければ 1 往復で終えてよい
- 上限は 4 往復。上限に達したら、残った点を未解決として 5 へ回す

## 5. 決まらない点を持ち主に聞く

- 双方に根拠があって決着しない点だけを、AskUserQuestion で聞く。選択肢ごとに Claude と Codex の根拠と不利を添える
- 時間切れと CLI の失敗は、意見の対立と分けて報告する

## 6. 計画ファイルを書いて共有する

- `.claude/plans/<YYYY-MM-DD>-<slug>.md` に書く（1 件 1 ファイル）。Go を受けて切った作業ブランチの最初の commit に入れる。
  合意した時点の記録で、実装の進み具合を書き足さない
- 節: 目的 / 対象外 / 方針 / 採った案と棄却した案（議論で比べたものだけ）/ 手順 / 検証 / リスク。冒頭に日付、Codex の session id と往復の数、持ち主の判断を書く
- 持ち主に「この計画で実装します」とパスと要点を共有し、**Go を待つ。**同じ範囲に Go が出ている依頼なら待たずに進む。実装中に範囲が変わったら、計画を直して Go を取り直す

## 7. 実装の後

差分のレビューは `codex-review` で頼む。
