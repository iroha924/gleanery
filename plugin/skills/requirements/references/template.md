# requirements.md の書き方

必要な節だけを使い、空の節を残さない。**解決方法（API、テーブル、画面の作り）を要件にしない。**
実装によって避けられない制約を書くときだけ、根拠の種類を区別して示す。

## 節

| 節 | 書くこと |
|---|---|
| 元の要求 | 利用者が最初に言ったことをそのまま残す。後から言い換えない |
| 現在の事実 | 調査で確かめたこと。出典（`path:line`、実行したコマンド、gleanery の記録）を付ける |
| 目的と成功条件 | 何が観測できれば実現したと言えるか |
| 用語 | この change で使う言葉と意味。コードや他の文書と呼び方が違うなら併記する |
| 対象の利用者 | 誰の、どの場面の話か |
| 機能要件 | `REQ-001` 形式の ID と、要件ごとの受け入れ条件 |
| 制約 | 変えてはいけないこと。根拠を付ける |
| 対象外 | やらないと決めたこと |
| 未解決事項 | 決まっていないこと。blocking かどうかと、誰が決めるか。利用者が決めることは、問いに保留と答えたものだけを置く |
| 参照 | 読んだ gleanery の記録、コード、issue、URL |

**REQ の ID は振り直さない。**design.md が ID で対応表を作るので、番号がずれると対応が黙って壊れる。
消した要件の ID も再利用しない。

**受け入れ条件は観測できる形で書く。**「使いやすい」「適切に扱う」ではなく、誰が何をすると何が見えるか。

## 根拠の区別

主張には次のどれかを付ける。区別が無いと、推測と古い記録が事実として次の工程へ渡る。

| 札 | 意味 | 添えるもの |
|---|---|---|
| 事実 | 現在のコード・設定・コマンド出力で確かめた | 出典 |
| 過去の判断 | gleanery の記録にある | 記録の出自（プロジェクト・記録・日付）と、現在のコードで確かめた範囲 |
| 推測 | 根拠はあるが直接は確かめていない | 根拠 |
| 決定 | 利用者がこの会話で問いに答えて決めたか、元の要求にある。エージェントが決めたものには付けない | 答えた問いの要約か「元の要求」。任されたときは「決定（委任）」と任された問いの要約 |

過去の判断と現在のコードが食い違うときは、コードを事実として書き、どちらを採るかは利用者に聞く（保留と答えたら未解決事項にする）。

## 形

```markdown
# <change の題>

## 元の要求

## 現在の事実

- 事実: ...（`server/src/x.ts:42`）

## 目的と成功条件

## 用語

- <言葉>: <意味>（<札>: <出典か答えた問いの要約>）

## 機能要件

### REQ-001 <要件>

受け入れ条件:

- <誰が何をすると、何が観測できるか>（<札>: <出典か答えた問いの要約>）

## 制約

## 対象外

- ...（決定: <答えた問いの要約>）

## 未解決事項

- [blocking] ...（決める人: 利用者。保留: <答えた問いの要約>）

## 参照
```
