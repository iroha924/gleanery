# design.md の書き方

承認済みの `requirements.md` を唯一の要求の入力にする。必要な節だけを使い、空の節を残さない。

## 節

| 節 | 書くこと |
|---|---|
| 対象と要約 | 対象の change、`requirements.md` の path、設計の要約 |
| 現在の構造 | いまどう動いているか。出典（`path:line`、実行したコマンド）を付ける |
| 採用する構造とデータフロー | 変更後の形。現在の構造と区別する |
| 変更するもの | データ、API、画面、CLI、Skill。変えるファイルの path |
| 認証・認可・信頼境界 | どこで入力を検査するか。secret をどこに置くか |
| エラーと境界条件 | 失敗、取消し、再試行、部分完了の扱い（要る範囲で） |
| 移行と互換性 | データを変えるなら migration、既存データ、role、RLS、rollback の判断 |
| 検証 | 決定的な検査（test、lint、型、スクリプト）と、review や人が見る検査を分けて書く |
| 代替案 | 採用案、主要な代替案、棄却理由、受け入れる不利な点 |
| 実装順 | 依存関係に沿った順序 |
| 未解決事項 | 決まっていないこと。blocking かどうか |
| REQ 対応表 | すべての `REQ-*` を、設計の要素と検証へ対応させる。**最後の節に置く**（SKILL.md の突き合わせがこの節から末尾までを見る） |

**現在の事実は一次情報から書く。**外部のライブラリやサービスは、入っている版の型定義か公式ドキュメントで
現行の形を確かめる。記憶で書くと、動くが古い形になる。

**mitos の過去の判断は、記録の出自を添えて書く。**現在のコードと食い違うときは、コードを事実として書き、
どちらを採るかは未解決事項にする。

## 形

```markdown
# <change の題> 設計

## 対象と要約

## 現在の構造

## 採用する構造とデータフロー

## 検証

- 決定的: `bun run test` で ...
- review・人: ...

## 代替案

| 案 | 採否 | 理由 | 受け入れる不利な点 |
|---|---|---|---|

## REQ 対応表

| REQ | 設計の要素 | 検証 |
|---|---|---|
| REQ-001 | ... | ... |
```
