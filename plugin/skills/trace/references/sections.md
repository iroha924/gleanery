## 判定の基準

各行を書く前に 1 つだけ問う。

> **この行を削ったら、半年後の読み手か次のセッションの AI が間違えるか。**間違えないなら削る。

書き終えたら、もう 1 つ問う。

> トレードオフも代替案も決定過程も書いていないなら、この記録は何のために存在するのか。

Google の Design Docs はこう書いている — 決定過程を書かない文書なら、最初からプログラムを
書いたほうがよかった。**「やったこと一覧」は git log が既に持っている。**

## 背景とゴール

`problem` は**症状ではなく損失**を書く。「バッチが遅い」ではなく「締め処理の開始が翌営業日に
ずれ、経理が当月の作業に入れない」。読み手が優先度を判断できる形にする。

`goal` は**測れる条件**にする。

| 書かない | 書く |
|---|---|
| 動くようにする | GET /invoices/:id が 200 で `{ id, url }` を返す |
| 速くする | バッチの所要時間が 30 分未満 |
| 直す | 再現テストを書き、それが通る |

`nonGoals` は**やらないと決めたこと**であって、単にやっていないことではない。
「PDF テンプレートの作り直し」のように、**やりたくなるが今回はやらない**ものを書く。

## 意思決定

**決定の価値は、選んだ案ではなく捨てた案にある。**採った案だけを書いた記録は、
半年後に同じ案を再検討させ、同じ理由で捨て直させる。

`context` は**中立な言葉で**書く。決定を正当化しない。そのとき働いていた力（技術的な制約、
期日、人の都合、組織の事情）をそのまま並べる。

`consequences` は**良いものだけを書かない。**Nygard の原典はここを明示している —
結果はすべて挙げよ、良いものだけではなく。受け入れた不利な点を `good: false` で残す。
それが後から「想定外の障害」として現れるのを防ぐ。

`confirmation` は他のテンプレートにほぼ無い欄で、**決定が実装で守られていることをどう
確かめるか**を書く。「9 月の本番実行のログでバッチが 30 分未満であることを見る」のように、
観測できる形にする。書けないなら、その決定は測れていない。

**覆した決定を消さない。**`superseded` にして後続を指す。消すと、次の人が元の案を再提案する。

## 経過（events）

**手順の実況を書かない。**「ファイルを開いた」「grep した」は残す価値がない。
残すのは**状態が変わった単位**と、**次の人の判断を変えるもの**。

| kind | 判定 |
|---|---|
| `work` | これが無いと、どこまで進んだか分からないか |
| `finding` | これを知らずに触ると間違えるか |
| `dead_end` | 次の人が同じ道を通る可能性があるか |
| `debt` | 見た人が「欠陥だ」と思って直しにいく可能性があるか |
| `state_transition` | `current` が変わったか |

`dead_end` が 1 件も無い記録には警告が出る。**本当に無かったなら問題ない。**
あったのに書いていないなら、次の人が同じ壁に当たる。

**`fact` を名乗るなら根拠を出す。**コマンドと exit code、コミット、ファイルと行、URL。
出せないものは `inference` にする。ここを曖昧にすると、そのときだけ真だったことが
恒久的な事実として残る。

**証拠は主張を支えるものを指す。自分の実装を指さない。**検査が見られるのは
「証拠が付いているか」までで、「その証拠が主張を支えているか」は見られない。
実測: 一次ソースを鉤括弧で引用した決定 3 件が、いずれも証拠欄に自分の実装ファイルを
書いた状態で検査を通った。レビュアーはそれを全件見つけた。

| 主張 | 支える証拠 | 支えない証拠 |
|---|---|---|
| 「Nygard は覆した決定を残せと書いている」 | その記事の URL | 自分が書いた SKILL.md |
| 「5,000 件でも parse は 3ms」 | 測ったコマンドと出力 | 上限を設けなかったコード |
| 「Codex では exit code が取れない」 | rollout を走査したコマンド | 取らないことにした実装 |

## 未解決の問い

`when` を 3 段階に分けるのは、**いつ解決される見込みかで扱いが変わる**ため。

| `when` | 扱い |
|---|---|
| `now` | これが埋まらないと進めない。`blocking: true` なら再開時の要約で先頭に出る |
| `during-implementation` | 手を動かすうちに決まる。止める必要はない |
| `out-of-scope` | この作業では決めない。**忘れないために残すだけ** |

`who` が `human` のものは、**AI が推測で埋めてはいけない**。業務判断、外部の資格情報、
要件そのものの変更がここに入る。

## 検証

**実行しなかったものを書かないのではなく、実行しなかったと書く。**
曖昧な完了宣言より、名指しされた欠落のほうが価値が高い。

修正を記録するときは、**修正前のコードで失敗することを確かめた**という事実も残す。
前後どちらでも通る検証は何も証明していない。

## 用語

**コードを読めば分かることは書かない。**関数名、ファイルの場所、依存関係は対象外。
書くのは、その組織・その業務でしか通じない語（「締め処理」「検収」「B 帳票」）。
前提を知らない読み手が最初に詰まるのはここ。

## 同じ事実を複数の節に書かない

**実測: HTML の目視ができない理由が 4 箇所、evals が通ったことが 5 箇所に書かれていた。**
読み手からは「同じ列挙と同じ阻害理由が繰り返される」と指摘された。

各事実には置き場所が 1 つだけある。

| 事実 | 置く場所 | 他の節での扱い |
|---|---|---|
| いつ何が起きたか | `events` | 参照するなら id で（`e-xxx`） |
| なぜそう決めたか | `decisions` | 同上（`d-xxx`） |
| 何を確かめたか | `verification` | 同上（`v-xxx`） |
| いまどうなっているか | `current` | 経緯は書かない。変化は `state_transition` へ |
| やらないと決めたこと | `background.nonGoals` | 決定に由来するなら 1 行で足り、理由は `decisions` にある |

## 書かないもの

| 書かない | 理由 |
|---|---|
| 会話の全文 | 記録に貼らず、`transcript` のパスだけ持つ。実体は必要になったときに読む |
| ツール出力の生ログ | 指し先（コマンドと exit code）だけ。長くすると拾われる確率が下がる |
| 感想、あいさつ、意気込み | 読み手の判断を変えない |
| 毎回同じ背景の書き直し | `background` は 1 箇所。追記のたびに再掲しない |
| コードベースから導けること | アーキテクチャ、ファイル一覧、依存関係 |

| 短さが retrieval 設計 | Lost in the Middle / context rot |
